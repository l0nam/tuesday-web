# Tuesday Web

Сайт Minecraft-проекта на Next.js 16, React 19, TypeScript, Tailwind CSS, Better Auth, Drizzle ORM и MySQL/MariaDB.

В приложении есть авторизация через Discord, профили игроков, внутренняя база сайта, статистика, города, магазин и API для игрового плагина. Для связи Discord-аккаунтов с Minecraft используется отдельная таблица DiscordSRV.

## Что передать заказчику

Лучше передать **весь репозиторий целиком** (доступ к GitHub или ZIP-архив исходников), а не собирать файлы вручную. В проекте есть серверные API-роуты, миграции, компоненты, ассеты и конфигурация, поэтому выборочная передача файлов легко ломает установку.

В комплекте должны остаться:

- `app/`, `components/`, `lib/`, `public/`, `scripts/`;
- `drizzle/` вместе с SQL-миграциями и `drizzle/meta/`;
- `package.json` и **`package-lock.json`**;
- `next.config.ts`, `tsconfig.json`, `drizzle.config.ts`, `components.json`, `eslint.config.mjs`, `instrumentation.ts`;
- `README.md` и `.env.example` (если он приложен к архиву).

Не передавать `.env`, `.env.local`, пароли БД, Discord Client Secret, токен бота, `BETTER_AUTH_SECRET`, `PLUGIN_API_SECRET`, дампы БД с личными данными, `node_modules/`, `.next/` и `.vercel/`. Секреты заказчик должен создать/получить самостоятельно и добавить непосредственно в настройки своего хостинга.

## Перед началом

Нужны:

1. Домен или поддомен с HTTPS.
2. Node.js **20.9 или новее**; предпочтительно поддерживаемая LTS-версия, совместимая с Next.js 16.
3. MySQL или MariaDB.
4. Discord-приложение в Discord Developer Portal с OAuth2 Client ID и Client Secret.
5. Доступ к настройкам базы, в которой DiscordSRV хранит связки Minecraft UUID и Discord ID.
6. Для интеграции с игровым плагином — его конфигурация, в которой можно указать URL сайта и общий секрет подписи запросов.

**Рекомендуемая схема:** собственная БД сайта `tuesday_web` и существующая БД Minecraft/DiscordSRV — могут находиться на одном MySQL/MariaDB-сервере, но права к ним должны быть разными. Сайт пишет только в свою БД и читает из базы DiscordSRV только два поля, необходимые для связи аккаунтов.

Если панельный хостинг блокирует внешние подключения к MySQL, обычно проще запустить сайт на том же сервере/в той же приватной сети. Не открывайте порт MySQL всему интернету только ради Vercel.

## Подготовка баз данных и пользователей

Названия ниже — примеры. Перед выполнением замените `SITE_HOST`, `DISCORDSRV_DB`, имя таблицы и пароли на реальные значения. Команды выполняются из phpMyAdmin/консоли с аккаунта, который **имеет право** создавать базы, пользователей и выдавать привилегии. На обычном панельном хостинге часть действий может выполняться через интерфейс панели.

### 1. Создайте отдельную БД сайта

Создайте пустую базу, например `tuesday_web`, с кодировкой `utf8mb4`. Не используйте для сайта базу игрового сервера как хранилище его собственных данных.

### 2. Создайте пользователя для приложения

Если у вас есть административные права MySQL/MariaDB, пример SQL:

```sql
CREATE USER 'tuesday_app'@'SITE_HOST'
  IDENTIFIED BY 'REPLACE_WITH_A_LONG_UNIQUE_PASSWORD';

GRANT ALL PRIVILEGES ON `tuesday_web`.*
  TO 'tuesday_app'@'SITE_HOST';
```

- Вместо `SITE_HOST` укажите хост, с которого приложение подключается к БД: следуйте значениям, разрешённым вашей панелью. Для сайта на том же сервере это может быть `localhost`; для удалённого сайта предпочтителен конкретный разрешённый IP. Не используйте `%` без необходимости.
- Эти права распространяются на `tuesday_web`, а не на весь сервер БД. Они нужны приложению и миграциям; глобальные права на все базы не нужны.
- Если базу создаёте в панели, создайте пользователя там же и назначьте ему права только на `tuesday_web`.

### 3. Создайте отдельного пользователя только для чтения DiscordSRV

Проверьте точное имя БД DiscordSRV, таблицы и колонок. В текущем приложении значения по умолчанию такие:

- таблица: `discordsrv_accounts`;
- Minecraft UUID: `uuid`;
- Discord ID: `discord`.

Если названия отличаются, исправьте их в переменных окружения далее. SQL-пример для стандартных названий:

```sql
CREATE USER 'tuesday_discordsrv_ro'@'SITE_HOST'
  IDENTIFIED BY 'ANOTHER_LONG_UNIQUE_PASSWORD';

GRANT SELECT (`uuid`, `discord`)
  ON `DISCORDSRV_DB`.`discordsrv_accounts`
  TO 'tuesday_discordsrv_ro'@'SITE_HOST';
```

`DISCORDSRV_DB` нужно заменить на имя существующей базы DiscordSRV. Такой пользователь может читать только указанные колонки конкретной таблицы — он не должен иметь `INSERT`, `UPDATE`, `DELETE`, `DROP`, `FILE`, `GRANT OPTION` или глобальных привилегий.

Проверьте права командой `SHOW GRANTS FOR 'tuesday_app'@'SITE_HOST';` и аналогично для `tuesday_discordsrv_ro`. Сам запрос `CREATE USER` не сработает, если панель запрещает создавать пользователей; в таком случае переходите к разделу [про один пользователь БД](#если-хостинг-позволяет-создать-только-одного-пользователя-бд).

### Важное про размещение БД

- **Сайт на том же сервере/в приватной сети:** используйте локальный/внутренний адрес БД, указанный хостингом. Порт MySQL не требуется публиковать в интернете.
- **Сайт на Vercel, БД на панельном хостинге:** удалённый доступ к MySQL должен поддерживаться провайдером; для него нужны TLS и разрешённый исходящий IP/сетевой маршрут. У Vercel не следует предполагать наличие одного постоянного IP для всех планов и конфигураций. Если панель не поддерживает безопасный удалённый доступ, используйте собственный сервер рядом с БД или отдельный защищённый API-мост — не открывайте порт `3306` всему миру.
- В паролях с символами вроде `@`, `:`, `/`, `#` и пробелами в URI нужно использовать URL-кодирование. Не вставляйте пароль в публичные сообщения.

## Настройка переменных окружения

Создайте `.env.local` локально или заполните раздел Environment Variables в панели хостинга/Vercel. **Не коммитьте настоящий env-файл в Git.**

### Обязательные переменные

| Переменная | Что указать |
|---|---|
| `DATABASE_URL` | URI БД сайта, например `mysql://tuesday_app:URL_ENCODED_PASSWORD@DB_HOST:3306/tuesday_web`. |
| `BETTER_AUTH_SECRET` | Случайный секрет не короче 32 символов. Не используйте пример или одинаковый секрет на разных сайтах. |
| `BETTER_AUTH_URL` | Канонический адрес сайта без завершающего слеша, например `https://example.com`. |
| `DISCORD_CLIENT_ID` | Client ID Discord-приложения. |
| `DISCORD_CLIENT_SECRET` | Client Secret того же Discord-приложения. |
| `PLUGIN_API_SECRET` | Секрет для HMAC-подписи запросов игрового плагина; не короче 32 символов. Укажите тот же секрет в конфигурации плагина. |

Сгенерировать секреты можно на доверенной машине с Node.js:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Первое значение подходит для `BETTER_AUTH_SECRET`, второе — для `PLUGIN_API_SECRET`. Не используйте один и тот же сгенерированный секрет для обоих параметров.

### Настройки БД

| Переменная | Значение / назначение |
|---|---|
| `DATABASE_SSL` | `false` для локального соединения без TLS; `true` для TLS с проверкой сертификата. В продакшене для удалённой БД используйте TLS с проверкой сертификата. |
| `DISCORDSRV_DATABASE_URL` | URI БД DiscordSRV с read-only пользователем. Необязательна для запуска сайта, но без неё функция поиска связи аккаунтов не работает. |
| `DISCORDSRV_DATABASE_SSL` | Режим TLS соединения DiscordSRV; если не задан, используется `DATABASE_SSL`. |
| `DISCORDSRV_TABLE` | Имя таблицы связей; по умолчанию `discordsrv_accounts`. |
| `DISCORDSRV_DISCORD_COLUMN` | Колонка Discord ID; по умолчанию `discord`. |
| `DISCORDSRV_UUID_COLUMN` | Колонка Minecraft UUID; по умолчанию `uuid`. |

### Необязательные настройки

| Переменная | Назначение |
|---|---|
| `SITE_TIMEZONE` | Часовой пояс для дат и статистики; по умолчанию `Europe/Moscow`. |
| `DISCORD_BOT_TOKEN` | Токен Discord-бота для отображения/обновления Discord-профиля и ролей на сайте. Хранить только на сервере. |
| `DISCORD_GUILD_ID` | ID Discord-сервера для проверки ролей. |
| `DISCORD_ROLE_ADMIN_ID` | ID роли администратора. |
| `DISCORD_ROLE_MODERATOR_ID` | ID роли модератора. |
| `DISCORD_ROLE_PLAYER_ID` | ID роли игрока. |
| `DISCORD_API_BASE` | Обычно не нужно менять; по умолчанию `https://discord.com/api/v10`. |

Без необязательных переменных ролей некоторые функции Discord просто не будут доступны. Не добавляйте префикс `NEXT_PUBLIC_` к секретам: они должны оставаться серверными.

### Настройте Discord OAuth2

В Discord Developer Portal откройте приложение сайта, раздел OAuth2 и добавьте Redirect URI:

```text
https://ВАШ-ДОМЕН/api/auth/callback/discord
```

URI должен совпадать с доменом из `BETTER_AUTH_URL` и быть указан с HTTPS в продакшене. Для локальной разработки отдельно используйте адрес localhost. Укажите соответствующие Client ID и Client Secret в переменных окружения.

## Способ 1. Установка на Vercel

Vercel подходит, если панельная БД доступна сайту по безопасному сетевому маршруту и её провайдер разрешает удалённые подключения.

1. Убедитесь, что репозиторий находится на GitHub и заказчик имеет к нему доступ.
2. Откройте [Vercel](https://vercel.com/), создайте проект и импортируйте репозиторий `l0nam/tuesday-web` (или репозиторий, который передан заказчику).
3. Оставьте Framework Preset `Next.js` и стандартную команду сборки `npm run build`. Не выбирайте Static Export: приложению нужны серверные маршруты, авторизация, база данных и API.
4. В настройках проекта откройте **Settings → Environment Variables** и добавьте обязательные переменные, переменные базы и нужные дополнительные значения. Задайте их для Production; Preview/Development настройте отдельно, если они используются. `BETTER_AUTH_URL` должен соответствовать продакшен-домену.
5. До первого рабочего деплоя выполните миграции БД по инструкции ниже. **Vercel не запускает `npm run db:migrate` автоматически** только потому, что он собирает проект.
6. Нажмите Deploy. Добавьте домен в настройках Vercel, настройте DNS и дождитесь выпуска HTTPS-сертификата.
7. Обновите Redirect URI в Discord Developer Portal на `https://ВАШ-ДОМЕН/api/auth/callback/discord`.
8. Если Minecraft-плагин отправляет события на API сайта, поменяйте URL и HMAC-секрет в конфигурации плагина. Используйте HTTPS.

### Миграции для Vercel

Миграции запускаются вручную из терминала с Node.js и установленными зависимостями либо в доверенном терминале хостинга, который может подключиться к БД:

```bash
npm ci
npm run db:migrate
```

Перед запуском передайте команде корректный `DATABASE_URL` через временный локальный `.env`/переменные терминала или настройку среды. Не добавляйте этот файл в Git и не вставляйте секреты в логи. Для миграций не используйте root: достаточно прав на базу сайта. После миграции выполните деплой/перезапуск приложения.

### Ограничения Vercel для этого проекта

Vercel запускает серверную логику в функциях, а не в одном постоянном процессе. В этом проекте `instrumentation.ts` запускает `setInterval` для периодического сбора истории онлайна сервера. **Такой постоянный таймер на Vercel не гарантируется**, поэтому график истории онлайна может не наполняться регулярно, хотя сайт и API могут работать. Для устойчивого сбора нужен постоянно работающий Node.js-процесс или отдельная запланированная задача/worker; текущему коду для переноса сбора на отдельный cron/worker потребуется доработка.

Также проверьте лимит соединений MySQL/MariaDB, доступность БД из Vercel и требования провайдера к IP/TLS. Если внешние подключения заблокированы, не открывайте БД всему интернету ради деплоя — выбирайте собственный хостинг в той же сети либо реализуйте защищённый API-мост.

## Способ 2. Установка на собственный хостинг

Подойдёт VPS или панельный хостинг, где разрешено запускать постоянно работающие Node.js-приложения. **Обычный Minecraft-хостинг не всегда поддерживает Node.js** — заранее проверьте, что панель даёт нужную версию Node.js, доступ к терминалу/командам и возможность держать процесс работающим постоянно.

### 1. Загрузите проект

Склонируйте репозиторий или загрузите ZIP-архив и распакуйте его в каталог сайта. Перейдите в корень проекта — туда, где находится `package.json`.

### 2. Установите зависимости

```bash
node --version
npm --version
npm ci
```

Убедитесь, что `node --version` показывает Node.js 20.9 или новее, совместимый с Next.js 16. `npm ci` использует зафиксированные версии из `package-lock.json`.

### 3. Настройте окружение

Создайте `.env.local` в корне проекта (рядом с `package.json`) и заполните значения из раздела [Настройка переменных окружения](#настройка-переменных-окружения). Укажите адрес БД, доступный **с самого Node.js-хостинга**; если БД находится на том же сервере, используйте внутренний адрес, который рекомендует провайдер.

Ограничьте права пользователя БД, используйте отдельный пароль и не публикуйте env-файл через веб-каталог.

### 4. Выполните миграции

Убедитесь, что создана пустая БД `tuesday_web` и `DATABASE_URL` указывает именно на неё:

```bash
npm run db:migrate
```

Папка `drizzle/` содержит версионированные SQL-миграции. Они создают структуру сайта. Не запускайте `npm run db:push` вслепую на рабочей БД; для установки и обновлений используйте миграции и делайте резервную копию перед изменениями.

Если требуется заполнить магазин данными из текущего скрипта проекта, **после проверки списка, цен и условий выдачи** можно запустить:

```bash
npm run db:seed
```

Этот шаг необязательный: скрипт добавляет демонстрационный/преднастроенный каталог магазина из `scripts/seed-shop.ts`. Сначала проверьте значения в файле и адаптируйте их под сервер заказчика. Повторный запуск обновляет текстовые поля, цены, режим выдачи, команды и сортировку товаров, поэтому не запускайте его без проверки на уже настроенном магазине.

### 5. Соберите и запустите приложение

```bash
npm run build
npm run start -- --hostname 127.0.0.1 --port 3000
```

Команда запуска должна оставаться работающей. Для продакшена настройте менеджер процессов, поддерживаемый хостингом (например, systemd/PM2 или менеджер Node.js в панели), чтобы приложение автоматически перезапускалось после сбоя и рестарта сервера. Не держите приложение только в интерактивной SSH-сессии, которая может закрыться.

Если панельный хостинг не позволяет слушать localhost/порт 3000 либо останавливает долгоживущие процессы, потребуется другой тариф/Node.js-хостинг или VPS.

### 6. Подключите домен и HTTPS

Рекомендуемая схема:

```text
Интернет
   |
   | HTTPS :443
   v
Nginx / Apache (reverse proxy)
   |
   | HTTP к 127.0.0.1:3000
   v
Next.js (Node.js)
   |
   +----> БД сайта (приватная сеть/localhost)
   |
   +----> БД DiscordSRV (read-only соединение)
```

Настройте Nginx/Apache как reverse proxy к `127.0.0.1:3000` и включите HTTPS. Не выставляйте порт приложения в интернет без необходимости. Обновите `BETTER_AUTH_URL` и Redirect URI Discord на фактический HTTPS-домен. Если сайт и Minecraft-сервер находятся на одном хостинге, всё равно лучше не открывать порт БД наружу, когда можно использовать внутреннее соединение.

## Если хостинг позволяет создать только одного пользователя БД

Это **не всегда означает, что нужно использовать root**. Сначала уточните у провайдера две разные вещи: запрещено ли создавать дополнительные логины и можно ли ограничивать права уже существующего логина на уровне отдельной базы/таблицы. Это не одно и то же.

### Вариант A — один логин, но ограниченные права

Если пользователь может иметь права на несколько баз, попросите провайдера (или администратора БД) выдать этому логину:

- права чтения/записи/миграций только на БД сайта `tuesday_web`;
- только `SELECT` колонок `uuid` и `discord` из таблицы DiscordSRV;
- никаких глобальных прав на `*.*`, администрирование пользователей, чтение файлов сервера БД или выдачу прав другим пользователям.

В этом случае `DATABASE_URL` и `DISCORDSRV_DATABASE_URL` могут содержать один и тот же логин/пароль, но у пользователя должны быть именно указанные ограниченные привилегии. Разные URI выбирают разные базы данных, а не создают отдельные права. Проверьте итог через `SHOW GRANTS`.

Права MySQL/MariaDB складываются: если у пользователя уже есть глобальный `ALL PRIVILEGES ON *.*`, добавление или отсутствие более узких прав не уберёт глобальный доступ. В таком случае попросите провайдера отозвать глобальные права или предоставить ограниченную учётную запись.

### Вариант B — единственный доступный логин фактически root/администратор

**Не указывайте такой логин в `DATABASE_URL` или `DISCORDSRV_DATABASE_URL` публичного сайта и не публикуйте MySQL-порт для всего интернета.** Если серверная часть сайта будет скомпрометирована, атакующий может получить все права этого логина: повредить/удалить базы, прочитать данные других клиентов и создать новых пользователей. HTTPS и сложный пароль не ограничивают последствия взлома приложения.

Безопасный порядок действий:

1. Сначала попросите поддержку хостинга создать отдельного пользователя с ограниченными правами или снять глобальные права с существующего логина.
2. Если панель этого не умеет, перенесите БД сайта на управляемую MySQL/MariaDB или отдельный сервер, где можно создавать пользователей. Оставьте Minecraft-БД приватной.
3. Если нужно лишь получать соответствия Minecraft UUID ↔ Discord ID из Minecraft-БД, можно разработать отдельный API-мост рядом с БД. Мост должен предоставлять только строго определённые read-only операции, использовать параметризованные запросы и проверку входных данных, принимать соединения только от сайта/разрешённых адресов, иметь HTTPS или приватный туннель, HMAC-подпись с защитой от повторов, ограничения частоты и журналирование. Не делайте endpoint, который принимает произвольный SQL.

API-мост потребует изменений кода: **текущая версия сайта подключается к DiscordSRV напрямую по `DISCORDSRV_DATABASE_URL` и не умеет использовать такой мост из коробки**. Если мост использует root/глобальный аккаунт на сервере, полный риск всё равно остаётся при компрометации самого моста — поэтому это компромисс, а не замена нормальным ограниченным правам. Не храните root-пароль в Vercel или в коде.

## Проверка после установки

1. Главная страница открывается по HTTPS и отображает статус Minecraft-сервера.
2. Вход через Discord возвращается на правильный домен. Если вход не работает, проверьте `BETTER_AUTH_URL`, Client ID/Secret и точное совпадение Redirect URI.
3. После первого входа профиль создаётся в БД сайта; страницы профиля, магазина и городов не возвращают ошибку БД.
4. Связанные Discord/Minecraft-аккаунты находятся, если `DISCORDSRV_DATABASE_URL` настроен и таблица/колонки соответствуют данным хостинга.
5. Если используется игровой плагин, проверьте правильность URL API и совпадение `PLUGIN_API_SECRET`. API отклоняет запросы с некорректной HMAC-подписью или устаревшим timestamp.
6. На постоянно работающем Node.js-хостинге проверьте накопление истории онлайна через некоторое время. На Vercel длительная работа периодического таймера не гарантируется (см. выше).

Для быстрой проверки сборки:

```bash
npm run build
```

Также в проекте есть вспомогательные сценарии `npm run test:smoke`, `npm run test:skin` и `npm run test:profile`. Тесты профиля используют локальную БД и выполняют очистку записей с тестовыми префиксами/UUID; запускайте их только после чтения кода теста и при явно выделенной тестовой БД. **Не запускайте тестовые сценарии на продакшен-БД.**

## Обновление сайта

1. Сделайте резервную копию БД сайта.
2. Получите обновлённый код (на собственном хостинге — `git pull` или новый архив; на Vercel — push в подключённую ветку).
3. Установите зависимости: `npm ci`.
4. Выполните `npm run db:migrate` с правильным `DATABASE_URL`.
5. Выполните `npm run build`.
6. Перезапустите процесс Node.js или дождитесь окончания деплоя Vercel.
7. Проверьте вход через Discord, профиль, API плагина и магазин.

## Резервные копии и безопасность

- Настройте регулярные резервные копии **как БД сайта, так и Minecraft/DiscordSRV БД**. Перед миграциями обязательно делайте резервную копию.
- Используйте разные, длинные пароли для пользователя сайта, пользователя DiscordSRV и OAuth/HMAC-секретов.
- Не передавайте заказчику свой Discord Client Secret, токен бота или личные пароли; заказчик должен владеть своими секретами.
- Не коммитьте `.env.local`, резервные копии БД или логи с токенами.
- Используйте HTTPS, обновляйте Node.js и зависимости, ограничьте доступ к административной панели и MySQL, включите TLS для удалённых подключений.
- Не давайте сайту глобальные привилегии, `FILE`, `GRANT OPTION` или административный доступ к серверу БД.
- Не используйте `DATABASE_SSL=no-verify` в продакшене, если можно установить корректный сертификат: этот режим отключает проверку сертификата.
- После настройки проверьте права каждого DB-пользователя через `SHOW GRANTS` и убедитесь, что пользователь DiscordSRV не может изменять данные.

## Частые проблемы

**Ошибка соединения с MySQL/MariaDB**
- Проверьте hostname, порт, имя базы, пользователя и пароль в URI.
- Проверьте, разрешены ли удалённые подключения и разрешён ли адрес хостинга сайта.
- Для удалённой БД проверьте TLS. Не решайте проблему открытием `3306` всему интернету.

**Сайт не может прочитать DiscordSRV**
- Проверьте `DISCORDSRV_DATABASE_URL`, права только на чтение, имя БД/таблицы и названия колонок.
- Стандартные названия в конфигурации: `discordsrv_accounts`, `uuid`, `discord`. Они должны соответствовать реальной таблице.
- Если соответствие аккаунтов не требуется, `DISCORDSRV_DATABASE_URL` можно оставить пустым — функция привязки/поиска DiscordSRV будет недоступна.

**Ошибка Discord OAuth**
- `BETTER_AUTH_URL` должен быть каноническим URL без завершающего слеша.
- Redirect URI должен в точности совпадать с URL в Discord Developer Portal, включая протокол и путь.
- Используйте Client Secret именно того приложения Discord, где настроен Redirect URI.

**Ошибки сессии после смены домена**
- Обновите `BETTER_AUTH_URL`, Redirect URI в Discord и переменные окружения целевого окружения.
- После изменения переменных выполните новый деплой или перезапуск Node.js-процесса.

**После деплоя не обновляется график онлайна**
- На собственном постоянно работающем Node.js-хостинге убедитесь, что процесс не останавливается.
- На Vercel текущий периодический таймер не гарантируется; для постоянных замеров понадобится отдельный worker/cron и соответствующая доработка приложения.
