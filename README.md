# Tuesday Web — инструкция по установке

Инструкция по установке сайта Minecraft-сервера Tuesday Web на Vercel или собственный хостинг.

Главный момент: **сайт использует две базы данных с разными задачами**. Первая хранит данные самого сайта, а вторая нужна для чтения связей между UUID игроков Minecraft и Discord ID из DiscordSRV.

## 1. Перед началом

Перед установкой подготовь:

- **Домен с HTTPS.** Для локальной разработки подойдёт `http://localhost:3000`.
- **Сервер с поддержкой Node.js.** Для текущей версии проекта Next.js 16 требуется Node.js 20.9 или новее. Рекомендуется использовать поддерживаемую LTS-версию, совместимую с проектом.
- **Базу данных MariaDB или MySQL** для сайта.
- **Discord OAuth2-приложение.** Его можно создать в [Discord Developer Portal](https://discord.com/developers/applications).
- **Доступ к базе данных DiscordSRV**, если сайт должен сопоставлять аккаунты Minecraft и Discord.
- **Настройки игрового плагина**, если используются API сайта и проверка запросов по HMAC-секрету.

### Как будут работать базы данных

Для сайта рекомендуется использовать отдельную базу `tuesday_web`.

Базу Minecraft-сервера и DiscordSRV можно оставить на том же сервере БД, но права доступа сайта должны быть ограничены:

- к `tuesday_web` сайт получает права, необходимые для работы и миграций;
- к базе DiscordSRV сайт получает только чтение нужных столбцов;
- сайт не должен получать административный доступ ко всему серверу БД.

Если хостинг не разрешает удалённые подключения к MySQL/MariaDB, размести сайт рядом с базой данных или настрой подключение через приватную сеть. **Не открывай порт MySQL/MariaDB для всех IP-адресов ради подключения сайта.**

## 2. Подготовка баз данных и пользователей

Выполни действия из этого раздела в панели хостинга или через SQL-клиент под учётной записью, которая имеет право создавать базы, пользователей и назначать привилегии.

Названия баз и таблиц ниже — примеры. Сверь их с настройками своего сервера.

### 2.1. Создай базу данных сайта

Создай отдельную базу `tuesday_web` и пользователя `tuesday_app`.

Пример SQL для MySQL/MariaDB:

```sql
CREATE DATABASE tuesday_web
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

CREATE USER 'tuesday_app'@'SITE_HOST'
  IDENTIFIED BY 'REPLACE_WITH_STRONG_PASSWORD';

GRANT SELECT, INSERT, UPDATE, DELETE,
      CREATE, ALTER, INDEX, DROP
ON tuesday_web.*
TO 'tuesday_app'@'SITE_HOST';
```

Замени:

- `SITE_HOST` — адрес, с которого разрешено подключаться приложению. Это может быть IP-адрес сервера сайта или другое значение, предусмотренное твоим хостингом.
- `REPLACE_WITH_STRONG_PASSWORD` — длинный уникальный пароль.

Если учётная запись уже создана, не создавай её повторно. Проверь её права и при необходимости скорректируй их.

Набор привилегий выше включает базовые операции, необходимые для работы сайта и выполнения миграций Drizzle. Возможности пользователей и доступные операции зависят от конфигурации MySQL/MariaDB и политики хостинга.

### 2.2. Подготовь доступ к DiscordSRV

В типовой конфигурации DiscordSRV хранит связи аккаунтов в таблице `discordsrv_accounts`:

- `uuid` — UUID игрока Minecraft;
- `discord` — Discord ID игрока.

Если у тебя используются другие названия таблицы или столбцов, укажи фактические значения в переменных окружения сайта.

Для чтения этих данных создай отдельного пользователя:

```sql
CREATE USER 'tuesday_discordsrv_ro'@'SITE_HOST'
  IDENTIFIED BY 'REPLACE_WITH_ANOTHER_STRONG_PASSWORD';

GRANT SELECT (uuid, discord)
ON DISCORDSRV_DB.discordsrv_accounts
TO 'tuesday_discordsrv_ro'@'SITE_HOST';
```

Замени `DISCORDSRV_DB` названием базы данных, которую использует DiscordSRV.

Этот пользователь должен иметь доступ только к необходимым данным. Не выдавай ему права на изменение записей, создание таблиц или управление другими базами.

Проверь итоговые привилегии:

```sql
SHOW GRANTS FOR 'tuesday_app'@'SITE_HOST';

SHOW GRANTS FOR 'tuesday_discordsrv_ro'@'SITE_HOST';
```

Если твой хостинг не поддерживает привилегии на уровне отдельных столбцов, уточни доступные варианты у провайдера. Не расширяй права пользователя без необходимости.

> **Важно:** ограниченные привилегии не отменяют более широкие права, которые уже выданы пользователю. Например, если ему ранее назначили глобальные `ALL PRIVILEGES ON *.*`, дополнительное ограничение на отдельную базу не сделает его ограниченным пользователем. Проверяй полный результат `SHOW GRANTS`.

## 3. Настройка переменных окружения

Проект использует переменные окружения для подключения к БД, авторизации через Discord и проверки запросов игрового плагина.

Не публикуй реальные пароли и секреты в документации, переписках, GitHub или клиентском коде.

### 3.1. Обязательные переменные

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Подключение к базе данных сайта |
| `BETTER_AUTH_SECRET` | Секрет Better Auth |
| `BETTER_AUTH_URL` | Основной URL сайта |
| `DISCORD_CLIENT_ID` | Client ID приложения Discord |
| `DISCORD_CLIENT_SECRET` | Client Secret приложения Discord |
| `PLUGIN_API_SECRET` | Секрет для проверки запросов игрового плагина |

Пример структуры:

```env
DATABASE_URL="mysql://tuesday_app:DB_PASSWORD@DB_HOST:3306/tuesday_web"

BETTER_AUTH_SECRET="GENERATED_AUTH_SECRET"
BETTER_AUTH_URL="https://ВАШ-ДОМЕН"

DISCORD_CLIENT_ID="YOUR_DISCORD_CLIENT_ID"
DISCORD_CLIENT_SECRET="YOUR_DISCORD_CLIENT_SECRET"

PLUGIN_API_SECRET="GENERATED_PLUGIN_SECRET"
```

Это шаблон: замени значения на свои. Не копируй его в production без настройки реальных данных.

### 3.2. Сгенерируй секреты

Установи Node.js, открой терминал и выполни:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

Команда сгенерирует случайное значение для `BETTER_AUTH_SECRET`.

Для `PLUGIN_API_SECRET` отдельно выполни:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Сохрани оба значения. **Для разных назначений используй разные секреты.** Значение `PLUGIN_API_SECRET` должно совпадать с секретом, настроенным на стороне игрового плагина.

### 3.3. Подключение к базе DiscordSRV

Добавь переменные:

```env
DISCORDSRV_DATABASE_URL="mysql://tuesday_discordsrv_ro:DB_PASSWORD@DB_HOST:3306/DISCORDSRV_DB"
DISCORDSRV_DATABASE_SSL="false"

DISCORDSRV_TABLE="discordsrv_accounts"
DISCORDSRV_DISCORD_COLUMN="discord"
DISCORDSRV_UUID_COLUMN="uuid"
```

В production значение `DISCORDSRV_DATABASE_SSL` нужно определить по настройкам подключения и требованиям хостинга. Если база данных находится на другом сервере, используй TLS с проверкой сертификата, когда это поддерживается.

Не оставляй примерные значения как есть: проверь имя базы, пользователя, адрес сервера и названия столбцов.

Дополнительная настройка соединений:

```env
DATABASE_SSL="false"
```

Для локальной разработки без TLS такое значение может быть допустимо. Для удалённой production-базы настрой защищённое соединение согласно требованиям провайдера. Не отключай проверку сертификата только ради устранения ошибки подключения.

Если пароль содержит специальные символы, например `@`, `:`, `/`, `#` или `%`, корректно закодируй их в URI подключения.

### 3.4. Дополнительные переменные

При необходимости настрой:

```env
SITE_TIMEZONE="Europe/Moscow"

DISCORD_BOT_TOKEN=""
DISCORD_GUILD_ID=""

DISCORD_ROLE_ADMIN_ID=""
DISCORD_ROLE_MODERATOR_ID=""
DISCORD_ROLE_PLAYER_ID=""

DISCORD_API_BASE="https://discord.com/api/v10"
```

`SITE_TIMEZONE` по умолчанию использует `Europe/Moscow`.

Токен Discord-бота, ID сервера и ID ролей нужны только для соответствующей функциональности. Если такая функция не используется, не заполняй необязательные переменные без необходимости.

**Не добавляй к секретам префикс `NEXT_PUBLIC_`.** Переменные с таким префиксом предназначены для клиентской части и не должны использоваться для паролей, токенов или приватных ключей.

### 3.5. Настрой Discord OAuth2

Открой [Discord Developer Portal](https://discord.com/developers/applications), выбери приложение и найди раздел OAuth2.

В Redirects добавь адрес обратного вызова:

```text
https://ВАШ-ДОМЕН/api/auth/callback/discord
```

Адрес должен точно совпадать с URL сайта и настройками Better Auth. Протокол, домен и путь имеют значение.

Для локальной разработки при необходимости добавь отдельный адрес:

```text
http://localhost:3000/api/auth/callback/discord
```

Не используй локальный адрес для production. Если домен меняется, проверь `BETTER_AUTH_URL` и Redirect URI в Discord Developer Portal.

## 4. Установка на Vercel

Vercel подходит для размещения Next.js-приложения, но имеет ограничения для фоновых задач и постоянных процессов.

### Шаг 1. Подключи репозиторий

1. Открой [Vercel](https://vercel.com/).
2. Импортируй репозиторий `l0nam/tuesday-web` или репозиторий заказчика.
3. Выбери проект на основе Next.js.
4. Проверь настройки сборки.

Обычно для проекта используются:

```text
Build Command: npm run build
```

Не включай `Static Export`: сайту нужны серверные функции и подключение к базе данных.

### Шаг 2. Добавь переменные окружения

Открой настройки проекта:

`Settings → Environment Variables`

Добавь переменные из раздела [«Настройка переменных окружения»](#3-настройка-переменных-окружения).

Проверь, что они назначены для нужных окружений — например, Production, а при необходимости и Preview.

Не храни секреты в исходном коде и не выводи значения переменных в логи.

### Шаг 3. Выполни миграции базы данных

**Не рассчитывай, что сборка Vercel автоматически создаст таблицы.** Перед первым запуском выполни миграции вручную из локальной копии репозитория или подходящего окружения с установленными зависимостями.

Например:

```bash
npm ci
npm run db:migrate
```

Перед выполнением убедись, что `DATABASE_URL` указывает именно на базу сайта и что у пользователя достаточно прав.

Не запускай миграции наугад против базы Minecraft-сервера или DiscordSRV. Перед повторными миграциями, изменением схемы или исправлением ошибок сохрани резервную копию базы.

### Шаг 4. Подключи домен

1. Добавь домен в настройках проекта Vercel.
2. Настрой DNS-записи согласно инструкциям Vercel.
3. Дождись выпуска HTTPS-сертификата.
4. Укажи итоговый URL в `BETTER_AUTH_URL`.
5. Обнови Redirect URI в Discord Developer Portal.

После изменения переменных окружения запусти повторное развёртывание, чтобы новое окружение использовало актуальные значения.

### Шаг 5. Учти ограничения фоновых задач

В проекте `instrumentation.ts` используется `setInterval` для накопления истории онлайна. В Vercel нельзя рассчитывать, что такой таймер будет непрерывно работать: серверные функции не являются постоянно запущенным Node.js-процессом.

Если история онлайна должна регулярно обновляться, потребуется отдельный механизм запуска: например, cron-задача, внешний worker или постоянно работающий сервер. Для этого могут понадобиться изменения в коде проекта.

Также проверь, что база данных разрешает подключения из окружения Vercel и не блокирует их из-за ограничений IP, TLS или лимита соединений.

**Не открывай порт 3306 всем адресам.** Используй разрешённые провайдером источники подключений, приватную сеть или другой защищённый способ доступа.

## 5. Установка на собственный хостинг

Этот вариант подходит для VPS или панели хостинга, которая позволяет запускать Node.js-приложения с постоянным процессом.

Не каждый Minecraft-хостинг поддерживает запуск Next.js. До установки проверь, можно ли запускать и держать работающим отдельное Node.js-приложение и подключаться к нужной базе данных.

### Шаг 1. Загрузи проект

Загрузи архив проекта или клонируй репозиторий. Перейди в папку сайта, где лежит `package.json`.

Проверь версии:

```bash
node --version
npm --version
```

Убедись, что используемая версия Node.js совместима с Next.js 16 и зависимостями проекта.

Затем установи зависимости:

```bash
npm ci
```

### Шаг 2. Создай файл окружения

Создай `.env.local` в корне проекта — рядом с `package.json`.

Добавь необходимые переменные из раздела [«Настройка переменных окружения»](#3-настройка-переменных-окружения).

Не помещай `.env.local` в публичную папку и не добавляй его в Git. Если панель предоставляет собственный менеджер переменных окружения, можно использовать его вместо файла — при условии, что приложение получает значения при запуске.

### Шаг 3. Создай таблицы

Выполни миграции:

```bash
npm run db:migrate
```

В проекте находятся SQL-миграции в каталоге `drizzle/`.

Перед изменениями схемы сделай резервную копию. Не используй `npm run db:push` вместо миграций автоматически: сначала проверь назначение команды и её последствия для текущей схемы.

### Шаг 4. Реши, нужен ли seed

В проекте есть команда:

```bash
npm run db:seed
```

Она запускает начальное заполнение данных магазина. Перед выполнением открой `scripts/seed-shop.ts` и проверь, какие товары и значения будут добавлены или изменены.

Повторный запуск может обновить текстовые поля, цены, способ выдачи, команды и порядок сортировки. Поэтому **не запускай seed вслепую на уже настроенном магазине**.

### Шаг 5. Собери и запусти сайт

Сначала выполни сборку:

```bash
npm run build
```

Затем запусти приложение:

```bash
npm run start -- --hostname 127.0.0.1 --port 3000
```

Не рассчитывай на то, что процесс останется работать после закрытия SSH-сессии. Для постоянной работы используй systemd, PM2 или менеджер процессов, предоставленный панелью хостинга.

### Шаг 6. Настрой HTTPS и прокси

Рекомендуемая схема:

```text
Пользователь
    |
    | HTTPS :443
    v
Nginx / Apache
    |
    | HTTP внутри сервера
    v
127.0.0.1:3000
    |
    v
MariaDB / MySQL
```

Настрой Nginx или Apache так, чтобы он проксировал запросы на локальный порт приложения. Базу данных по возможности держи в приватной сети или на localhost.

В production сайт должен открываться по HTTPS. После настройки домена проверь авторизацию Discord и обнови OAuth Redirect URI.

## 6. Если можно создать только одного пользователя БД

Сначала выясни у провайдера две вещи:

1. Запрещено ли создавать дополнительные учётные записи MySQL/MariaDB?
2. Можно ли ограничить привилегии уже существующего пользователя?

Это разные ограничения: запрет на создание дополнительных пользователей не обязательно означает, что у существующего пользователя должны быть административные права.

### Вариант A. Один пользователь с ограниченными правами

Если создать две учётные записи нельзя, иногда можно использовать одного пользователя для обеих баз. Однако его привилегии должны покрывать только необходимые действия:

- чтение и изменение данных сайта в `tuesday_web`;
- чтение столбцов `uuid` и `discord` в таблице DiscordSRV;
- дополнительные операции, необходимые для выполнения миграций.

В таком случае обе переменные подключения могут использовать одни и те же учётные данные:

```env
DATABASE_URL="mysql://USER:PASSWORD@DB_HOST:3306/tuesday_web"

DISCORDSRV_DATABASE_URL="mysql://USER:PASSWORD@DB_HOST:3306/DISCORDSRV_DB"
```

Разные URI **не разделяют права** одного пользователя. Доступ ограничивается только привилегиями на сервере MySQL/MariaDB.

После настройки проверь:

```sql
SHOW GRANTS FOR 'USER'@'SITE_HOST';
```

Если у пользователя есть глобальные права, например `ALL PRIVILEGES ON *.*`, он по-прежнему может иметь доступ к другим базам. Для публичного сайта это нежелательно.

### Вариант B. Хостинг предоставляет только административную учётную запись

**Не используй root или другого администратора БД в `DATABASE_URL` или `DISCORDSRV_DATABASE_URL` публичного сайта.**

Если приложение скомпрометируют, атакующий может получить административный доступ ко всем доступным базам, изменить или удалить данные и создавать другие учётные записи.

Предпочтительный порядок действий:

1. Попроси провайдера создать ограниченного пользователя.
2. Если это невозможно, размести базу сайта на другом сервере или отдельном управляемом сервисе БД.
3. Если сайту необходимы данные DiscordSRV, рассмотри отдельный API-мост рядом с базой, который выполняет только строго определённые операции чтения.

API-мост не должен принимать произвольный SQL. Он должен проверять входные данные, использовать параметризованные запросы, ограничивать допустимые адреса источников, защищать соединение и иметь ограничение частоты запросов. Для запросов плагина также необходима корректная проверка HMAC и защита от повторного использования запросов.

API-мост не устраняет риск полностью: если его сервер использует root-доступ и будет скомпрометирован, база по-прежнему окажется под угрозой.

**Не храни пароль root в Vercel, исходном коде или публичном репозитории.** Если сейчас есть только административный пользователь и нет возможности ограничить его права, сначала реши вопрос с безопасной архитектурой подключения и только потом разворачивай сайт.

**Не запускай такие тесты против production-базы.** Используй отдельную тестовую базу и проверь, какие данные удаляют тесты, прежде чем выполнять их.

## 8. Обновление сайта

Перед каждым обновлением сделай резервную копию базы сайта. Если обновление затрагивает данные Minecraft или DiscordSRV, сохрани и их копии.

### Порядок обновления

1. Получи новую версию кода: выполни `git pull` для нужной ветки или загрузи новый архив.

2. Установи зависимости:

   ```bash
   npm ci
   ```

3. Выполни миграции:

   ```bash
   npm run db:migrate
   ```

4. Собери проект:

   ```bash
   npm run build
   ```

5. Перезапусти приложение на собственном хостинге или дождись окончания нового развёртывания на Vercel.

6. Проверь авторизацию Discord, профили, магазин и API игрового плагина.

Перед миграцией убедись, что `DATABASE_URL` указывает на правильную базу. Не запускай обновление схемы против базы Minecraft или DiscordSRV.

Не запускай `npm run db:seed` при каждом обновлении автоматически: сначала проверь, требуется ли повторное заполнение данных магазина.

## 9. Резервные копии и безопасность

Перед запуском сайта в production проверь следующее:

- **Резервные копии.** Регулярно сохраняй базу сайта и отдельно базу Minecraft/DiscordSRV, если от неё зависит работа сайта.
- **Отдельные пароли.** Используй длинные уникальные пароли для учётных записей. Секреты авторизации и плагина также должны быть отдельными.
- **Владение секретами.** Заказчик должен хранить собственные пароли БД, Discord Client Secret и токены бота. Не используй для его проекта свои личные токены или секреты других проектов.
- **Git.** Не коммить `.env.local`, дампы баз, резервные копии и логи с токенами.
- **HTTPS.** Используй HTTPS для публичного сайта и защищённое соединение для удалённой БД.
- **Обновления.** Поддерживай Node.js и зависимости проекта в актуальном совместимом состоянии.
- **Доступ к панели.** Ограничь доступ к панели администратора и базе данных.
- **Права MySQL/MariaDB.** Не выдавай публичному приложению глобальные привилегии, `FILE`, `GRANT OPTION` или другие административные права без конкретной необходимости.
- **Проверка TLS.** Не используй `DATABASE_SSL` с отключённой проверкой сертификата в production, если провайдер позволяет настроить сертификат, которому можно доверять.

После настройки ещё раз выполни `SHOW GRANTS` для пользователей БД и убедись, что пользователь DiscordSRV имеет только необходимые права чтения.

## 10. Частые проблемы

### Не удаётся подключиться к базе данных

Проверь:

- адрес и порт сервера БД;
- имя базы, пользователя и пароль;
- разрешён ли доступ с сервера, на котором работает сайт;
- ограничения IP-адресов и лимит подключений;
- настройки TLS и сертификата.

Не решай ошибку подключения открытием порта 3306 для всего интернета.

### Не работают данные DiscordSRV

Проверь переменные:

```env
DISCORDSRV_DATABASE_URL
DISCORDSRV_DATABASE_SSL
DISCORDSRV_TABLE
DISCORDSRV_DISCORD_COLUMN
DISCORDSRV_UUID_COLUMN
```

Убедись, что названия базы, таблицы и столбцов соответствуют твоей установке DiscordSRV. Проверь права пользователя: ему необходим доступ на чтение нужных данных.

Если на твоём сервере используются нестандартные названия таблиц или столбцов, значения по умолчанию `discordsrv_accounts`, `discord` и `uuid` не подойдут без изменений.

### Не работает авторизация через Discord

Проверь `BETTER_AUTH_URL` и Redirect URI в Discord Developer Portal. Домен, протокол и путь `/api/auth/callback/discord` должны совпадать с фактическим адресом сайта.

После изменения настроек перезапусти приложение или выполни новое развёртывание, чтобы изменения переменных окружения вступили в силу.

### После смены домена авторизация перестала работать

Обнови:

- `BETTER_AUTH_URL`;
- Redirect URI в Discord Developer Portal;
- настройки домена и HTTPS.

Затем перезапусти приложение или выполни повторное развёртывание.

### Не обновляется график онлайна

На собственном хостинге проверь, что Node.js-процесс постоянно работает и не завершается после закрытия SSH-сессии.

На Vercel `setInterval` не гарантирует постоянного накопления истории. Для этой задачи потребуется cron, отдельный worker или постоянно работающий процесс с соответствующей настройкой кода.

### Миграция не выполняется

Проверь `DATABASE_URL`, доступ пользователя и права на создание или изменение таблиц.

Убедись, что миграция направлена в базу `tuesday_web`, а не в базу Minecraft-сервера или DiscordSRV. Перед повторным запуском посмотри текст ошибки и сохрани резервную копию, если схема могла измениться частично.

---

**Последнее действие перед запуском:** проверь реальные адреса баз данных и пользователей, убедись, что сайт не использует административную учётную запись MySQL/MariaDB, и только после этого запускай миграции и открывай сайт для игроков.
